      About this advisor, and what it does not model

      Every rule on partitioned tables was observed on a lab copy of a 24-month SALES table on Oracle 19.27, or comes from the 19c documentation; each finding says which, and says inferred when a combination was not run. The rules on plain tables, histograms, indexes and invalidation come from the 19c SQL Tuning Guide and the DBMS_STATS reference. The lab log is in docs/lab-observations.md.

      • Blocks are estimates using average partition size. Row samples are costed as full passes; histogram samples, segment allocation and index work can make actual I/O differ. The collector uses the largest partition change percentage for all changed partitions, so a mix of fresh and stale partitions can overestimate reads.
      • The automatic job is inferred from schema GATHER AUTO tests on 19.27. The real nightly task was not run in that lab. AUTO_CASCADE index counts are observations, not a guarantee that every index is always gathered.
      • Unverified combinations include force with individual partition locks, synopsis format migrations, and new histogram or column-group work under the automatic job. Non-incremental APPROX_GLOBAL AND PARTITION aggregation is represented by an upper bound.
      • Subpartitions. Modelled. GRANULARITY AUTO gathers the subpartition level for LIST and RANGE subpartitions (lab CP1, CP2: 9 of 9) and not for HASH (lab J, C1: 6 of 6 partitions analysed, 0 of 24 subpartitions). Synopses are partition-level in every case observed (CP4, CP7). With INCREMENTAL, DML in one LIST or RANGE subpartition makes the gather read the whole parent partition plus that subpartition (CP5, CP6), up to twice the partition; a HASH partition is read once (lab J). Without INCREMENTAL a LIST or RANGE composite takes a third pass (CP8). GRANULARITY ALL behaved like AUTO there (CP7); ALL or SUBPARTITION on HASH subpartitions was not run and the page says inferred. partname with a subpartition name is not modelled.
      • Partition exchange. Modelled for an exchange since the last gather. The gather reads nothing only if three things hold together: the empty target partition was gathered first, the staging table has a table-level synopsis (INCREMENTAL TRUE, INCREMENTAL_LEVEL TABLE) and both sides have the same histograms (lab H2, H5, H6, H7, V3, Tg). An exchange done by a job, or a different order of steps, was not run.
      • Column groups are proposed from what the dictionary already recorded: a SQL plan directive with equality predicates, or a group SEED_COL_USAGE captured. The form does not read your SQL, so a correlated pair no query has misestimated yet is not found; expressions are looked for only in cached plans (see the health check below). The directive's equality flag decides the proposal (column group statistics serve equality, in-list and GROUP BY). Observed on 19.27 (lab CG1); the costs on an incremental table are lab E4 and Tc.
      • Degree and concurrency change how long a gather takes, not what it reads. They are shown, not modelled.
      • Real-time and high-frequency statistics are modelled as settings that change what the gather finds, not as running mechanisms. Oracle licenses both only for Exadata and Exadata Cloud in 19c (Licensing Information, Table 1-8), although the parameter and the preferences exist on every edition. The high-frequency task (AUTO_TASK_STATUS, AUTO_TASK_INTERVAL, AUTO_TASK_MAX_RUN_TIME) was not run on the lab, and real-time statistics are not available there, so both rest on the documentation. Online statistics for bulk loads (STATS_ON_LOAD, GATHER AUTO) are modelled from the documentation (the SQL Tuning Guide, bulk-load statistics).
      • Pending statistics are modelled as a recipe (gather with PUBLISH FALSE, test with OPTIMIZER_USE_PENDING_STATISTICS, compare, publish or delete); the lab observations are G1, G1c and Tf.
      • The health check of the real table reads the collector's detail block. Its rules are heuristics over dictionary data, not proof that a plan is bad. Index usage (DBA_INDEX_USAGE) is sampled, so an index shown as unused may have been used. Expression candidates come from the predicates of plans still cached in V$SQL_PLAN, which is weak evidence (a plan that aged out or never ran leaves no trace; one positive case on the lab, Q11). DML counters are flushed periodically, so a forecast of days until the table is stale is only as current as the last flush; the collector flushes them when it may. The checks were developed against one 19.27 lab database and the 19c documentation. A statement the collector user may not run drops its records, and the section that needs them says so.
      • Other patch levels. Lab observations are from 19.27 and may vary across 19c release updates. REPORT_GATHER_TABLE_STATS reports affected objects without collecting statistics; it does not measure physical reads. The 19c reference omits its OPTIONS argument, but 19.27 accepts options => 'GATHER AUTO', so the dry run passes the call's options through.
      Written for Oracle Database 19c. A companion to Optimizer Statistics, explained. No server, no tracking: everything runs in this page.
